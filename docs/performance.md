# Оптимизация PageSpeed — 11 октября 2026

Задача: получить более 90 баллов во всех четырёх категориях на мобильном
и настольном устройстве, сохранив согласованный дизайн и Метрику 33578164.

## Исходное состояние

Отчёт: https://pagespeed.web.dev/analysis/https-urbaso-ru/bdeux4x4kv?form_factor=mobile

| Устройство | Производительность | Доступность | Рекомендации | SEO |
|---|---:|---:|---:|---:|
| Мобильное | 70 | 100 | 96 | 92 |
| Настольное | 86 | 100 | 96 | 92 |

Мобильные LCP 11 с, FCP 2,1 с, TBT 20 мс, CLS 0. Настольный LCP 2 с.
Эти цифры относятся к исходному публичному отчёту, а не к локальному серверу.

Исходный main: `22fc0324edce4f4fec3ecf7bc65ff75a8e823cb9`.
При установке подтверждён фактический HEAD VPS
`b08e39e019ec237ab8071cc4f6da90ad757cea15`. Его дерево полностью совпадает
с исходным main: `ed568397764b8e1acf70f561e1cce716e3fa357f`.
Установщик сохраняет фактический серверный коммит для отката и учитывает
единственный подтверждённый `skip-worktree` у неиспользуемого
`assets/images/hero/code-fragment.webp`, не меняя сам файл и флаг.
Локальный baseline в подготовленном архиве с точным опубликованным счётчиком:
`fe0e14721d4a3829d9852a6d6819e64bc3c7c1f8`.
SHA256 опубликованного baseline `index.html`:
`b7d49ffe13355047a76f2e6fe040b44f2b81b22cf0b3b8a3e80126fdeddd2e81`.
При публикации через GitHub сохранены те же файлы baseline и оптимизации;
метаданные новых коммитов отличаются, поэтому их SHA другие. Для установки
и восстановления использовать точные SHA из выданной команды и резервной копии.

## Изменения

- Для изображений созданы варианты нужных размеров с `srcset`/`sizes`,
  размерами и нативной отложенной загрузкой. Первый экран получает приоритет.
  Портрет использует оригинальные байты во всех размерах экрана.
- Исходные изображения и шрифты сохранены. Ссылки просмотра сертификатов
  и рекомендаций продолжают открывать полноразмерные оригиналы. Внутри
  диалогов нет `srcset`, который мог бы перекрыть выбранный JavaScript `src`.
- Начальная загрузка Inter и Caveat уменьшена с 523 928 до 102 856 байт.
  Переменные оси и метрики сохранены. Дополнительные символы доступны через
  отдельные полные языковые поднаборы `@font-face`.
- Стили собраны в один минифицированный файл с сохранением порядка правил
  и всех адаптивных состояний. Декоративные бумага и линии оформлены фонами,
  чтобы сохранить художественные пропорции без ошибок растяжения контентных
  изображений в Lighthouse.
- Фоны разделов «Как я работаю» и FAQ загружаются за 600 px до появления
  в окне. Без JavaScript или IntersectionObserver действует обычный CSS.
  Активные изображения FAQ предварительно загружаются рядом с разделом,
  используя те же адреса, что и CSS.
- Hero инициализируется один раз; события изменения окна объединяются через
  `requestAnimationFrame`. Измерения предшествуют записи стилей.
- Добавлен `meta description`, исправлены роли панелей FAQ.
- Подготовлены scoped gzip и immutable-кеш для файлов с хешем содержимого.
  HTML и прежние адреса ресурсов сохраняют `no-cache`.
- Счётчик Метрики, ссылки, тексты услуг и контакты сохранены.

## Сборка

Сайт остаётся статическим: сборочные зависимости нужны только разработчику.
Готовые ресурсы входят в Git и устанавливаются без Node.js на VPS.

1. Установить зависимости из `scripts/README-media.md`, а также
   `tinycss2==1.4.0` и `rcssmin==1.2.1` для Python.
2. Выполнить `node scripts/build-media.mjs`.
3. Выполнить `python3 scripts/build-css.py` и взять поле `stylesheet` из вывода.
4. Выполнить `python3 scripts/build-page.py --stylesheet /assets/optimized/site-HASH.css`.
5. Проверить страницу и добавить исходники, manifest, новые ресурсы и HTML
   одним коммитом. Не удалять опубликованные старые ресурсы во время обычной
   пересборки: их может использовать открытая вкладка.

`build-page.py` можно запускать повторно. Исключение для подчёркивания заголовка
«Как я работаю» сохраняет исходную геометрию inline-блока: у него нет `sizes=auto`.

## Проверка и установка

Проверяются ширины 320, 390, 768, 900, 1024, 1440 px, изменение размеров окна,
все вкладки FAQ, клавиатура, диалоги документов, контакты и отсутствие ошибок
JavaScript/загрузки. Отдельно проверяются фактический `currentSrc` документов,
появление фоновых изображений после прокрутки и резервное поведение без IO.

Локальный Lighthouse 13.5.0 запускается с gzip, на headless Chrome и без
внешнего скрипта Метрики, чтобы не отправлять тестовые просмотры в рабочий
счётчик. Такие замеры показывают результат оптимизации собственных ресурсов,
но не заменяют Google PageSpeed на действующем домене.

## Публичная проверка после установки

Релиз `31e4f1006cdcf304dcb0a0b048234cdea6909c7d` установлен на VPS.
Проверены gzip, кеширование, совпадение опубликованных ресурсов с Git,
редиректы и защита служебных путей: 34 HTTP-проверки пройдены. На публичном
сайте работают просмотр и переключение сертификатов, увеличение оригинала
рекомендательного письма, закрытие через Escape и переключение FAQ с клавиатуры.

Цель по производительности пока не подтверждена. В настольных замерах
TBT составил 357 и 269 мс, Speed Index — 2,74 и 1,82 с. Длительные задачи
есть как у самой страницы, так и у Метрики; нельзя приписывать весь TBT
счётчику или сравнивать эти результаты с локальными замерами без него.

Первый публичный отчёт указал `img.grid` (декоративную SVG-сетку первого
экрана) как LCP-элемент с отложенной загрузкой. Следующая точечная правка
меняет только его `loading` на `eager` и добавляет `fetchpriority="high"`.
Источник, размеры и оформление сохранены; блок Метрики побайтово прежний.
Повторная сборка страницы идентична. Эта правка устраняет позднее обнаружение
конкретного изображения, но сама по себе не гарантирует снижение TBT или
оценку выше 90. После её установки нужен новый публичный замер.

После установки `2b94cc927f56ec6200367d8674f6325d8b71636b` отчёт
[516zorhd4m](https://pagespeed.web.dev/analysis/https-urbaso-ru/516zorhd4m?form_factor=mobile)
дал 83/100/100/100 на обоих устройствах. Мобильный LCP — 4,40 с, TBT —
78 мс; настольный LCP — 0,81 с, TBT — 308 мс. Улучшение одной загрузкой
SVG не подтверждено. Мобильный LCP-элемент — `img.grid-paper-top`.
В публичных сетевых аудитах собственные ресурсы отмечены HTTP/1.1. Проверка
на VPS подтвердила HTTP/1.1 через IPv4 и IPv6 для трёх имён сайта, с проверкой
сертификатов и SNI. Установлен Nginx 1.24.0 с модулем HTTP/2, но он не включён.
Остальные проекты используют те же сокеты 443: включение `listen ... http2`
затронет и их. Серверные настройки этим обновлением не меняются.

Подготовлены responsive preload мобильной бумаги и установка настольной
геометрии до содержимого hero. Источники изображений и формулы размеров
сохранены: 20 настольных сценариев совпадают с действующим runtime,
18 мобильных/планшетных не меняются. Сборка идемпотентна; остальной HTML,
включая Метрику, сохранён. Изолированное сравнение без Метрики дало mobile
96→96, desktop 100→99, CLS 0 в обоих вариантах. Эти локальные результаты
не подтверждают прирост публичной оценки и не заменяют проверку после установки.

Дополнительный локальный A/B выявил дорогую растеризацию цепочки из восьми
`drop-shadow` у портрета. В настольном trace длительная задача главного потока
почти не использовала его CPU, одновременно выполнялись тяжёлые RasterTask.
Подсказка `will-change: filter` только портрету сохранила исходный фильтр и
снизила суммарное время RasterTask с 1372 до 119 мс, максимальную задачу —
со 114 до 9,1 мс; TBT с 27 до 0 мс. LCP остался 0,56 с. Это локальный тест
без Метрики, а не новая оценка PageSpeed действующего сайта; точный вклад
этой причины в публичные 308 мс TBT по одному отчёту определить нельзя.
Свежий мобильный контроль дал LCP 3,69 с / TBT 201 мс, вариант с отдельным
слоем — 3,31 с / 8 мс и при повторе 2,85 с / 17 мс. Суммарная растеризация
сократилась с 646 до 60 и 25 мс; CLS во всех трёх запусках — 0. Разброс
абсолютных времён сохраняется, устойчивый эффект подтверждён для растеризации.
Визуальная проверка этой версии в облачном браузере до установки недоступна:
он не подключается к локальному серверу и не разрешает открывать file URL.
Исходное изображение, цепочка фильтров, остальные CSS-правила и Метрика
сверены побайтно; внешний вид и действия нужно проверить после установки.
Отдельный план HTTP/2, требующий согласования общего серверного эффекта:
[performance-http2-plan.md](performance-http2-plan.md).

TBT 59 мс / CLS 0,000573 / SI 2,50 с. Цель строго выше 90 ещё не достигнута.
Оба хоста прошли 13 HTTP-проверок. В браузере проверены первый экран,
отсутствие горизонтального переполнения при ширине 1363px, просмотр и

и вкладки FAQ с клавиатуры. Мобильный первый экран просмотрен в filmstrip PSI.

В том же публичном мобильном отчёте единственный блокирующий CSS-запрос
занял интервал 1216–2301 мс. Фоны и отложенные изображения первого экрана
начали загружаться после него. Следующее изменение помещает точные байты
собранного CSS в `<style>` на прежней позиции перед Метрикой. Внешний запрос
исключается; каскад, URL ресурсов и все правила сохраняются. Исходники CSS
и собранный файл остаются в Git, повторная сборка обновляет встроенную копию.
Preload шрифтов и бумаги остаётся перед стилями; JavaScript для CSS не нужен.

Локальный изолированный A/B без Метрики: mobile 90→95, FCP 904→805 мс,
LCP 3685→2929 мс, TBT 28→26 мс, SI 1191→900 мс, CLS 0 в обоих вариантах.
Desktop со встроенными стилями — 100, LCP 603 мс и TBT 0. Первый запрос
переносит CSS внутрь HTML: сумма gzip-байтов HTML и CSS увеличивается на
297 байт при уровне сжатия 5. Ответ HTML 200 становится примерно на 20 КБ
больше; отдельное кеширование CSS для этой страницы больше не используется.
Это обмен небольшого объёма повторных ответов 200 на исключение блокирующего
запроса при первом посещении. Публичный эффект проверяется после установки.

Критерий приёмки — каждая категория выше 90, основные действия работают,
дизайн соответствует исходному. Полевые Core Web Vitals, если они доступны,
обновляются отдельно от лабораторного измерения и не меняются мгновенно.
